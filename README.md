# Support2Fix

Support2Fix is an AI platform that turns a customer support issue into an evidence-backed engineering investigation. The flow runs: root cause → reproduction → validated fix → human-approved pull request → customer response.

> **Status: Phase 2 (authentication and organizations).** Users, organizations, memberships with roles, session auth, RBAC and tenant isolation are implemented and tested against a real Postgres. Tickets, agents and everything else land in later phases — see the roadmap in [ADR-001](docs/decisions/001-architecture.md).

## Running locally

### Option A — Docker Compose (recommended once Docker is installed)

Requires Docker Desktop (WSL2 backend on Windows).

```bash
cp .env.example .env
docker compose up --build
```

- Frontend: http://localhost:3000
- API: http://localhost:8000 (docs at `/docs`)
- Postgres: `localhost:5432` (user/password/db: `support2fix` by default)

### Option B — Run the apps directly (no Docker)

Two terminals, from the repo root.

**Postgres** (once): install PostgreSQL 17 natively (on Windows: `winget install PostgreSQL.PostgreSQL.17`), then create the app role and the dev + test databases:

```sql
-- as the postgres superuser, e.g. psql -U postgres -h 127.0.0.1
CREATE ROLE support2fix LOGIN PASSWORD 'support2fix';
CREATE DATABASE support2fix OWNER support2fix;
CREATE DATABASE support2fix_test OWNER support2fix;
```

**API** (needs Python 3.11+):

```bash
cd apps/api
python -m venv .venv
./.venv/Scripts/pip install -e ".[dev]"   # macOS/Linux: source .venv/bin/activate first
./.venv/Scripts/python -m alembic upgrade head
./.venv/Scripts/python -m uvicorn app.main:app --reload --port 8000
```

Without a database the API still starts: `/api/v1/health` reports `degraded`, and anything that needs the database returns an error.

**Web:**

```bash
cd apps/web
npm install
npm run dev
```

Then open http://localhost:3000/dashboard. The Next.js dev server proxies `/api/*` to `http://localhost:8000` (configurable via `API_ORIGIN`), so no CORS setup is needed — see [ADR-001 D10](docs/decisions/001-architecture.md).

### Health checks

- `GET /health` — liveness only, no dependency checks.
- `GET /api/v1/health` — checks the database. Returns `503 {"status": "degraded", "database": "unreachable"}` instead of crashing when Postgres isn't reachable. The dashboard's status pill reflects this.

### Database migrations

```bash
cd apps/api
./.venv/Scripts/python -m alembic upgrade head        # apply
./.venv/Scripts/python -m alembic downgrade base      # roll everything back
./.venv/Scripts/python -m alembic revision --autogenerate -m "describe change"
```

Always review an autogenerated migration, and check that it survives an `upgrade → downgrade → upgrade` round-trip. Autogenerate misses some things; for example, dropping a table doesn't drop a native Postgres enum type it used.

## API (Phase 2)

Interactive docs: http://localhost:8000/docs. Mutating requests (POST/PATCH/PUT/DELETE under `/api/`) must send `X-Requested-With: support2fix`, the CSRF defense described in [security.md §10](docs/architecture/security.md). The frontend's API client adds it automatically.

| Endpoint | Who | Notes |
|---|---|---|
| `POST /api/v1/auth/register` | anyone | Creates a user, a new organization and an ADMIN membership, then logs in |
| `POST /api/v1/auth/login` | anyone | Sets an `HttpOnly` session cookie |
| `POST /api/v1/auth/logout` | signed in | Deletes the session server-side, so the cookie stops working immediately |
| `GET /api/v1/auth/me` | signed in | User, memberships, active organization |
| `POST /api/v1/auth/switch-org` | signed in | Only to an organization you're a member of |
| `GET /api/v1/organizations/current` | any member | |
| `PATCH /api/v1/organizations/current` | ADMIN | Rename |
| `GET /api/v1/organizations/current/members` | any member | |
| `POST /api/v1/organizations/current/members` | ADMIN | Add an existing user by email, with a role |
| `PATCH /api/v1/organizations/current/members/{user_id}` | ADMIN | Change role |
| `DELETE /api/v1/organizations/current/members/{user_id}` | ADMIN | Remove |

Organization routes always act on the caller's *active* organization, taken from their session. No route accepts an organization id from the client, which is what keeps one organization's data out of another's reach. The last ADMIN of an organization can't be demoted or removed. Errors use RFC 9457 `application/problem+json`.

## Testing and quality checks

**API:** tests that need a database use `TEST_DATABASE_URL` (default: the local `support2fix_test` database). If it isn't reachable those tests are skipped with the reason shown, and the rest still run.

```bash
cd apps/api
./.venv/Scripts/python -m pytest -q          # add -rs to see skip reasons
./.venv/Scripts/python -m ruff check .
./.venv/Scripts/python -m ruff format --check .
./.venv/Scripts/python -m mypy app
```

**Web:**

```bash
cd apps/web
npm run test        # vitest
npm run typecheck   # tsc --noEmit
npm run lint        # eslint
npm run format      # prettier --check
npm run build       # production build
```

All of the above are green as of Phase 2: 23 API tests against a real Postgres, 3 web tests.

## Environment variables

See [.env.example](.env.example). Defaults match the local setup above (`support2fix`/`support2fix` on `localhost:5432`), and `LLM_MODE=fake` means no LLM API key is needed yet. The session cookie's `Secure` flag defaults to on only when `ENVIRONMENT=production`, because a Secure cookie is never sent back over plain `http://` in local development.
